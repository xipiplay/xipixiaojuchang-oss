# 嬉皮小剧场 · 剧本自动化（外部智能体接力）

## 分工（先读这一节）

- **你是调度员**：下命令、读进度、把请求分给子智能体、检查结果、向用户汇报。
  **你自己不读剧本正文，也不亲手写分割 / 提取 / 分镜**：那会撑爆你的上下文，也不是你的活。
- **子智能体是「文字模型」**：软件原来把这些请求发给用户接入的 API，现在放进一个收件目录，由子智能体（也就是你们自己的模型）回答。子智能体就是那个 API——只管把输入加工成要求的格式，不做别的。
- **只覆盖文字流程。生图、生视频不在这里**：它们走用户自己的图片 / 视频 API，要花钱。文字流程跑完后，汇报「生图卡几张、生视频卡几张」，让用户在软件里自己点生成。
- **推理分镜必须等用户审核分割之后、明确同意才能做**（见「审核闸门」）。用户要自己看分割的效果，你不能替他决定。
- **（调度员模式）只管你这次被要求跑的那个项目**；**监听模式例外**：用户自己在软件里点按钮，点的是哪个项目就做哪个项目（见「监听模式」）。用户可能同时在软件里手动操作别的项目（接力开着时，他手动触发的分集 / 分割 / 提取也会进收件箱等人回答）：那些请求**不是你的活**——不分配、不回答、不取消，汇报时提一句让用户知道。
- 不要直接改软件的数据文件（`project.json`、`shots.json`…），所有操作只走命令；不要动别的项目。

## 硬规则：回答必须由模型亲自写（违反 = 做错，整批结果作废）

软件对收到的回答照单全收，不会分辨是模型写的还是脚本造的。所以这里必须自觉：

1. **每个请求都要有一个模型**（子智能体；你所在的平台没有子智能体，就由你自己）**读完 `user.txt`、遵照 `system.txt`、亲手写出回答。**
2. **禁止写程序去批量"生成"回答**：不许用正则、模板、关键词匹配、按字数 / 句数机械切分来造分割、素材描述、分镜。脚本只能做**搬运**（读请求、写回答文件、批量发命令、统计进度）。
3. **禁止从别处抄素材**：提取出的角色、场景、道具，分割的内容，分镜的内容，**只能来自本请求的 `user.txt`**。不许读软件数据目录里别的项目（`ScriptPipelines/`、别的项目文件夹）、桌面上的参考文本、历史词典来填答案——那会把别的项目的人物和设定混进这个项目。
4. **平台没有子智能体 / 额度不够，不是用脚本凑数的理由。**没有子智能体：你自己一个请求一个请求地读、写，慢就慢，先告诉用户会很慢。额度不够：停下，如实汇报做到哪、剩多少没做。
5. **唯一的例外：剧本分集。**原文里有明确的「第 N 集」标题时，软件自己就会在本地按标题切（不用你做）；万一要你来答 AI 分集，也可以用程序按标题切（几万字原样抄一遍，程序比模型更不容易漏字），但必须原样保留正文、不增不减、**标题行留在每集正文开头**，并在汇报里明说这一步是程序切的。其他任何步骤都没有例外。
6. **汇报里必须写明每个阶段的回答是怎么产生的**：几个请求、由几个子智能体 / 你自己逐个写出；若有程序参与，说清楚程序做了什么。不许含糊成「已完成」。

## 硬规则：待回答的请求一个都不许漏，汇报「完成」之前必须核对（违反 = 报假完成）

2026-10-10 出过事：一部剧本批量分割，56 个请求答了 53 个就报了「完成」，剩下 3 个还在软件里等着回答——智能体把它们当成「之前取消的旧请求」跳过了。这三条就是防这个：

1. **待回答列表里有的，就是软件还在等的。**软件取消一个请求时，会把请求文件删掉、同时把它从待回答列表里去掉，所以取消过的请求**不会**再出现在列表里。不许凭印象、凭数目（「还剩 3 条，应该就是之前取消的那 3 条」）判断它是旧的、已取消的，更不许因此跳过。**判断取消以待回答列表为准**：列表里还在 = 没取消。子智能体回报 `CANCELLED` 时，主智能体必须用 `xipi pending` 复核——这个 id 还在列表里，就不是取消（多半是子智能体看的收件目录不对；`xipi` 现在会明说「收件目录不对」，退出码 4），重派并写明 `--dir`。真做不了的请求用 `xipi fail <id> "原因"`，让软件如实记成失败，**不许悄悄跳过**。
2. **汇报「完成」之前必须运行 `xipi done --project <本次项目>`，退出码 0 才能说完成**（它核对两件事：这个项目没有待回答的请求；批量任务 `finished` 为真）。退出码 5 = 没完成，照它列出来的继续做。**不许用自己数出来的数字代替**（「已分割 53 集」不等于完成）。汇报里附上它的输出和 `xipi status` 的数字。
3. **`--project` 要和软件里的项目名（或 id）完全一样**，比如项目叫「项目 72」就不能只写「72」。写错时 `xipi` 会报错并列出现有项目；不会再悄悄把你这个项目的请求当成「别的项目的」——那条「不碰别的项目的请求」的红线，只对**真的**别的项目有效。**子智能体派活时要写明收件目录**：把 `xipi check` 输出里的「目录」原样告诉它，它的每条 `xipi` 命令都带 `--dir <收件目录>`（沙箱里它的默认目录可能不是软件在用的那个）。
4. **一次请求很多时分批发命令**：超过 20 集的剧本，`split` / `infer` / `extract` 的 `episodes` 一次最多 15~20 集，这一批 `xipi done` 通过了再发下一批（同一个项目同一时间只能跑一种批量任务，本来也得等上一批结束）。每轮活短，漏了也能早发现。

## 工具

本目录里的 `xipi.py`（Python 标准库，无需安装）。下面把 `python3 <本目录>/xipi.py` 简写作 `xipi`；
每次调用都写完整路径，或先 `XIPI="python3 <本目录>/xipi.py"` 再 `$XIPI check`（别用 alias，非交互 shell 里不生效）。
「子智能体」指你所在平台的后台子任务（Claude Code 里是 Agent 工具，开成后台运行）。

| 谁用 | 命令 | 作用 |
|---|---|---|
| 主 | `xipi check` | 预检：软件在线、接力开着（退出码 0 才能开工） |
| 主 | `xipi status [--project <id或名字>]` | 进度摘要；`--json` 给原始数据 |
| 主 | `xipi pending --project <id或名字>` | 待回答的请求（id、类型、项目、集号、已领 / 未领、等了多久）。**一律带 `--project`**：只列你这次任务那个项目的，别的项目的只报个数。「已领」= 已有子智能体在做，别重复分配 |
| 主 | `xipi done [--project <id或名字>]` | **汇报「完成」之前必跑**：没有待回答的请求、批量任务已结束，退出码 0 才能说完成；5 = 没完成（列出缺什么）。见上面「待回答的请求一个都不许漏」 |
| 主 | `xipi cmd '<json>'` | 发一条命令，等软件受理（受理 ≠ 做完） |
| 监听 | `xipi wait [--timeout 50] [--project <id或名字>]` | 阻塞到用户在软件里点出新请求就返回（并替你认领）；超时退出码 4，软件离线退出码 1 |
| 子 | `xipi unpack <id>` | 把请求拆成 `system.txt` / `user.txt` / `meta.json`，同时登记「已领取」（软件据此知道你在干活） |
| 子 | `xipi answer <id> [文件]` | 提交回答（默认读 `answer.txt`） |
| 子 | `xipi fail <id> "原因"` | 做不了时报告失败 |

目录默认 `~/Library/Application Support/XipixiaojuchangOpen/AgentBridge/`（`--dir` 或环境变量 `XIPI_BRIDGE` 可改）。

## 监听模式：用户点哪一步，你做哪一步（像接入的 API 一样）

用户不让你跑整部剧本，而是**自己在软件里点按钮**（AI 分集 / 时长分割 / 分段命名 / 场景·角色·道具提取 / 推理分镜 等文字步骤），你只在旁边**守着，来一个请求做一个**——软件原来把请求发给文字模型 API，现在由你来当那个 API。完整的可粘贴指令见本目录的 `监听模式指令.md`。

和调度员模式的区别：

| | 调度员模式 | 监听模式 |
|---|---|---|
| 谁决定跑什么 | 你发 `xipi cmd` | **用户**在软件里点 |
| 管哪个项目 | 只管被要求的那个 | **所有项目**（用户点哪个项目就做哪个；用户限定了就带 `--project`） |
| 审核闸门 | 推理分镜前要用户明确同意 | **没有**——用户亲手点「推理分镜」就是同意 |
| `xipi cmd` | 用 | **不用、不发任何命令**（不 split / extract / infer / stop） |
| 汇报 | 闸门汇报 + 最终汇报 | 不主动刷屏：做完一批一句话（几个、什么类型、有无失败）；用户问了再详说 |

**循环**（直到用户说停）：

1. `xipi check` 通过才开始（不通过按「第 0 步」的提示告诉用户）。
   **开场确认（每次开始监听问一次，按你自己的平台来）**：先弄清你的平台**派子智能体时能选什么**——能不能指定模型、能不能指定思考强度 / 推理档位，具体有哪几个可选。**只列你真的能选的，别编**；有的平台派活时直接带参数，有的要用户先建好子智能体的配置文件（Codex 就是后者，见下面「子智能体分档」）。然后问用户一次、等他回答再开工，**按请求类型分别问**，每项给出你的建议——分集 / 分割是机械整理，建议最快的、思考低；推理分镜直接决定视频质量，建议最强的、思考高；提取场景 / 角色 / 道具要写描述，建议强的：
   > 子智能体的模型和思考强度，你想怎么分？我这边能选的是：〈列出你真能选的模型 / 档位〉。
   > - 剧本分集 / 时长分割：建议〈最快的〉，思考〈低〉
   > - 分段命名：建议〈快的〉，思考〈中〉（要判断年龄阶段、沿用前面各集的名字，但输出很短）
   > - 推理分镜：建议〈最强的〉，思考〈高〉
   > - 提取场景 / 角色 / 道具：建议〈强的〉，思考〈中或高〉
   > 回「好」就按建议；想改直接说。
   用户说了算，**本次监听照他说的派**；中途被打断后他说「继续监听」，沿用上次的选择，不再问。你的平台派子智能体时**选不了模型**，就一句话告诉用户「我这边选不了，都用默认的」，然后直接开工，别反复问。用户要**改选择**时：你能直接改的就改；要靠配置文件才能改的平台（比如 Codex 的 `~/.codex/agents/*.toml`），告诉他改哪个文件、改哪一行、改完要不要重开——你在派活时口头要求，平台不一定会真换。第一批做完后问他一句速度和质量对不对，别替平台打包票。
2. `xipi wait --timeout 50 --max-active 4`：没请求时它自己阻塞着等，**不用你 sleep、不用你轮询**。`--max-active 4` 让 xipi 按收件目录里「已领未答」的真实数目算空位，一次只交出空位那么多个，其余留在软件的队列里——一次点 50 集你也只会拿到 4 个，**不用自己数在做几个，也不用记还有哪些 id 在排队**；4 个都在做时它会继续等，直到有人做完。
   - 退出码 **4**（没有新请求）：什么都不用说，**立刻再 `wait`**。
   - 退出码 **1**（软件离线 / 接力没开）：告诉用户一次，然后每分钟再 `wait` 一次，软件回来自己恢复，别反复刷屏。
   - 退出码 **0**：输出里每行一个请求（id、类型、项目、第几集），**已替你登记认领**（左栏图标变绿，不会再重复交给你）。
3. 对每个请求起**一个**后台子智能体（按开场确认的选择派：用你平台的办法让这个子智能体用选定的模型和思考强度；请求的类型在 `wait` 输出的第二列；Codex 不会自动选，派活时要**明确写**「用 xipi_fast 子智能体」或「用 xipi_strong 子智能体」；**同时最多 4 个**：用户的 API 限 40 请求/分钟，每个子智能体做一个请求要调 6~9 次模型，起步时几个子智能体的前几次调用会挤在同一分钟里，开多了先撞限流；平台报限流 / 额度 / 并发上限的错，就把并发减半再派，别原样硬重试；用户的额度更大时由用户来改这个数；id 从 `xipi wait` 的输出里逐字复制进提示词），用下面「子智能体任务模板」逐字照做（`unpack` → 写 → `answer`）；你的平台没有子智能体，就自己一个一个做。**派完立刻回到第 2 步**，别等它们做完——它们做的时候新的请求会继续来。
4. 子智能体 `failed` 或崩了：请求还在待回答里（`xipi wait --reclaim-after 0 --no-claim` 能看到）就重派，**最多再试 2 次**；还不行 `xipi fail <id> "原因"`，如实告诉用户。
5. 认领超过 30 分钟、请求还在 = 领的人没干完（崩了 / 对话被关了），`wait` 会自动重新交出来。

注意：
- **硬规则全部照旧**：每个回答必须由模型亲自读、亲自写；不许写脚本批量生成；不许读别的项目的数据；平台没额度就停下如实说，不是用脚本凑数的理由（见上面「硬规则」）。
- 推理分镜请求是软件一集一集**串行**放出的，同一时刻通常只有一个，这是故意的（下一集要承接上一集最后一段）。
- **待回答列表里有的请求一个都不许跳过**：不许凭印象、凭数目当成旧的或已取消的；取消以待回答列表为准（子智能体报 CANCELLED、请求却还在列表里，就是它的目录不对，重派并写 `--dir`）；做不了用 `xipi fail`（见「待回答的请求一个都不许漏」）。用户问你「做完了吗」之前，先跑 `xipi done`。
- 用户在软件里点「取消 / 停止」：请求文件会被删掉，`unpack` / `answer` 提示 CANCELLED，丢弃即可。
- **请求 id 必须逐字复制**（从 `xipi wait` / `xipi pending` 的输出里复制），不许凭记忆手打——写错一个字符（`15718ca6` 写成 `15718ca3`），`xipi` 找不到文件，看起来就像「已取消」。`xipi` 现在会提示「这个 id 写错了」并给出最像的那个；看到这个提示就用它给的 id 重做，不是取消。
- 不提交任何生图 / 生视频（不替用户点生成）；不改软件数据文件；不动用户没点出来的东西。
- 你的运行环境如果限制了单次运行时长或工具调用数，被打断后用户说一句「继续监听」，你从第 1 步重新开始就行（`wait` 会把没人领的请求交给你）。

### 子智能体分档（模型和思考强度）

分割是机械整理（把原文按时间标号切开），快最重要；推理分镜直接决定视频质量，宁可慢也要想透。所以不同的请求最好用不同的模型和思考强度——**选什么由用户定，你只负责读懂自己平台能选什么、列给他、按他说的派**（见监听循环第 1 步的「开场确认」）。不同平台的做法不一样，你自己看平台的文档 / 能力，不要套别的平台的说法。

**Codex 的做法**（官方：模型和思考强度写在每个自定义子智能体的配置文件里，派活时点名使用）：本 skill 文件夹的 `codex-agents/` 里有两个现成模板——

| 文件 | 建议管哪些请求 | 默认思考强度 |
|---|---|---|
| `xipi_fast.toml` | 剧本分集、时长分割 | `low` |
| `xipi_strong.toml` | 推理分镜、提取场景、提取角色、提取道具（分段命名也可以放这里；想省钱用快档 + 中档思考） | `high` |

用户把两个文件复制到 `~/.codex/agents/`，把 `model` 那行的 `#` 去掉、改成他账号里快 / 强的模型名（不改就继承主会话的模型，不会报错），重新打开 Codex。Codex 同时开的子智能体上限（`agents.max_threads`，默认 6）比我们的 4 大，不用改。社区有人反馈配了却继承了主会话的模型（没法证实），所以第一批做完后，如果用户觉得分割并没有变快，让他确认实际用的模型。

## 第 0 步：开工前检查（每次都做）

1. `xipi check` 必须通过。不通过就停下，告诉用户：**打开软件 → 设置 → 剧本流水线 → 打开「外部智能体接力」→ 保存**。软件要一直开着、电脑不要睡眠。
2. 提醒用户：跑的时候别在软件里操作（导入剧本会切到新项目页面）。用户能在软件左栏「AI」图标的右上角看到状态：**黄点 = 接力已开、在等智能体；绿点 = 智能体在工作**（发过命令、领了请求或交了回答之后一分钟内，或有请求被领走还没交回答，都算在工作）。你发出第一条命令（如 `ping`）后，黄点就会变绿。
3. **沙箱 / 权限**：`xipi check` 报 `Operation not permitted` 或找不到目录时——
   - 让用户把文件夹 `~/Library/Application Support/XipixiaojuchangOpen/AgentBridge/` 授权给你（Gemini：Connected Folders；Codex：工作区 / 权限设置）。这个目录是唯一需要的，`xipi.py` 的工作文件也放在它里面的 `work/`，不用别的目录。
   - 沙箱里 `$HOME` 常常不是 `/Users/<用户名>`：用 `--dir "/Users/<用户名>/Library/Application Support/XipixiaojuchangOpen/AgentBridge"`（或环境变量 `XIPI_BRIDGE`）写绝对路径。
   - 实在跑不了 `xipi.py`：照文末「附录：手写协议」直接读写文件，格式是同一个。
4. 弄清要跑**哪部剧本**：
   - 用户给了 TXT 文件路径 → 走「导入」。**导入前先 `xipi status`：已有同名（或明显是同一部）的项目，就问用户「复用已有的，还是新建一个」**，别擅自新建（`import-script` 每次都会新建项目，软件只会给重名的自动加序号）。
   - 用户说的是软件里已有的项目名 → `xipi status` 里找它，拿到 `id`；已经分过集 / 分割过的步骤不用重做。
   - 要跑的集范围：默认全部；用户说「第 1 到 5 集」就用集号数组（集号从 1 起）。

## 命令（`xipi cmd '<json>'`）

| 命令 | 例子 | 说明 |
|---|---|---|
| ping | `{"cmd":"ping"}` | 确认在线 |
| import-script | `{"cmd":"import-script","file":"/绝对路径/剧本.txt","name":"可选"}` | 建新项目 + 存剧本 + 分集（剧本里有至少两处「第 N 集」标题就由软件在本地按标题切，不调用 AI、很快；没有标题才走 AI 分集）。返回新项目的 `project` id。`"split":false` 只导入不分集 |
| split | `{"cmd":"split","project":"<id>","episodes":[1,2,3]}` | 批量「时长分割」。`episodes` 省略或 `"all"` = 全部集。已经分割过的集会被新结果**整个替换**。用户对这次重分有特别要求（比如「把第 2、3 段合并」「第 4 段拆成两段」），把他的话原样放进 `"note"` |
| name | `{"cmd":"name","project":"<id>","episodes":[1,2,3]}` | **分段命名**：给每一集的每一段写【场景】【角色】【道具】【本段在场】四行（有人在回忆 / 闪回里时多一行【阶段】：周承山=四十岁），写回这一段文字的最上面（分割只管切，名字归这一步）。一集一集按顺序跑（每一集带着前面各集已用的名字，同一个对象沿用同一个写法）；这几集必须先 split 过；**做完才能 infer**（软件拒绝没命名的集：「还没有命名」）。已经命名过的集会被重新命名覆盖。`"note"` 同上 |
| extract | `{"cmd":"extract","project":"<id>","kinds":["角色","场景","道具"],"episodes":"all"}` | 提取素材，在生图页建卡片（不动已有卡）。**名字取自各集分镜卡的头行 `[场景][角色][道具]`**，AI 只给这些名字写描述（角色、道具去原文里找，场景去用到它的分镜里找），所以选中的集要先 `infer`，没推理分镜的会被拒绝（「还没有推理分镜」）。名字多会拆成几个请求（一类最多同时 3 个）。`kinds` 省略 = 三类都做。`"note"` 同上（只对这一次生效）。**只想提取个别名字**（用户说「只重提周承山」「补一个漏掉的道具」）：加 `"names":["周承山"]`（头行里的名字，一字不差），并把 `kinds` 限到那一类；不带 `names` 就是选中各集这一类的**全部**名字——已经有卡的再提会多出一张「名字 2」，别为了补一个名字把整类重提 |
| infer | `{"cmd":"infer","project":"<id>","episodes":[1,2],"approved":true}` | 推理分镜，在生视频页建卡。一集一集按顺序跑；这几集必须先 split 过；**做完才能 extract**。**`approved:true` 只能在用户明确同意之后才加**；不带，软件直接拒绝。`"note"` 同上 |
| stop | `{"cmd":"stop","project":"<id>"}` | 停掉这个项目里所有在跑的 AI 任务（已完成的保留） |

软件当场回受理结果：`ok: true` 才算发起了；`ok: false` 时 `message` 写着原因（项目不存在、集号越界、上一轮没跑完、这几集还没分割…），**按原因处理，不要原样重发**。
同一个项目同一时间只能跑一种批量任务（split / name / infer 互斥；extract 的三类可以一起跑，但不能和 split / name / infer 同时）。

## 流程（五个阶段加一个 2.5「命名」，严格按顺序；阶段 2.5 和 3 之间有审核闸门）

每个阶段：**发命令 → 调度循环（下面）→ 判定完成 → 检查 → 失败的重试 → 才进下一阶段**。

| 阶段 | 命令 | 软件会发出的请求类型 | 完成判定（读 `xipi status`） |
|---|---|---|---|
| 1 分集 | `import-script`（已有项目则跳过） | 剧本分集（1 个，整部剧本；有「第 N 集」标题时软件本地切，否则 AI 切） | 项目出现 `N 集`，且没有进行中的任务 |
| 2 分割 | `split` | 时长分割（每集 1 个，同时放出） | 批量任务 `split` 的 `finished` 为真，且 `xipi done` 通过 |
| 2.5 命名 | `name` | 分段命名（每集 1 个，按集顺序一个一个来：每集要带着前面各集的名字） | 批量任务 `name` 的 `finished` 为真，且 `xipi done` 通过；`xipi status` 里「已命名」= 已分割的集数 |
| ⛔ 闸门 | — | — | 阶段 2.5 做完后**停下**，向用户汇报，等明确同意（见下一节） |
| 3 推理 | `infer`（带 `"approved":true`） | 推理分镜（每集 1 个，按集顺序一个一个来） | 批量任务 `infer` 的 `finished` 为真，且 `xipi done` 通过 |
| 4 提取 | `extract` | 提取角色 / 场景 / 道具：名字取自刚推理出的分镜头行；每类 1~几个请求（名字多会拆批，同时放出） | 批量任务 `extract` 的 `finished` 为真，且 `xipi done` 通过 |
| 5 汇报 | — | — | 见「汇报」 |

### ⛔ 审核闸门（阶段 2.5 做完之后、阶段 3 之前）

用户要先看分割的效果，**同意之前不许进阶段 3，也不许发 `infer`**，即使用户之前说过「全部跑完」。

1. 阶段 2 和 2.5 做完并检查完（失败的已经重试过），**停下来，向用户汇报**：
   - 每一集分割是否成功；失败的集和软件的原话；
   - 请用户去软件里看：**剧本页 → 「时长分割」**（每段最上面是命名写的四行名字，必要时多一行【阶段】），或工作台里点开某一段（上面格子是名字、下面格子是这 30 秒的剧情），那里能直接看、直接改；
   - 最后问一句：「分割效果确认没问题的话，回复『同意』，我就开始推理分镜、再提取素材；要跑哪几集？」
2. **等用户明确同意**。「同意」「可以」「继续」算；沉默、「看看」、「嗯」不算。
3. 同意只对**这次汇报里列出的集**有效（用户另外指定了范围就按他说的）。以后新增的集、重做过的集，要再汇报、再同意。
4. 用户审核时可能已经在软件里改了分割。推理读的是软件里**现在的**分割内容，所以：
   - 闸门等待期间**不要**重发 `split`（会覆盖他的修改）；
   - 他要求某几集重新分割，先确认一句「这会覆盖你对这几集的修改，确定吗」，他确认了再发 `split`，做完回到第 1 步重新汇报。
5. 拿到同意后才发 `infer`，并在命令里带上 `"approved":true`；用户同意的集号写进 `episodes`。推理分镜做完（并检查完）后接着发 `extract`（范围同 `infer` 的集），不用再问。

### 调度循环（每个阶段里反复做，间隔约 5 秒，别更勤）

1. `xipi pending --project <本次项目>` / `xipi status --project <本次项目>`。`xipi status` 标出「离线或接力已关」（状态文件超过 15 秒没更新）→ 先等一轮再确认；仍然离线 = 软件没开或接力被关，停下问用户。
2. 对每个**还没分配、且属于本次项目**的待回答请求，在并发上限内（同时最多 4 个子智能体；平台报限流 / 额度的错就减半再派）各起一个**后台子智能体**，提示词用下面的「子智能体任务模板」，只填请求 id（从 `xipi pending` 的输出里逐字复制，别手打）。记下 id 已分配，别重复分配；派完用 `xipi pending` 对一遍，还有没被领走的就补派。
3. 一个请求从待回答列表里消失 = 已回答 / 已取消 / 已超时，不用管。**反过来，还在列表里的就是软件还在等的**，不许当成旧的、已取消的跳过（见「待回答的请求一个都不许漏」）。
4. 子智能体回报 `failed` 或自己崩了，而请求还在待回答列表里 → 释放这个 id 重新分配，**最多再试 2 次**；还不行就让软件把它记成失败：`xipi fail <id> "子智能体多次失败：…"`。
5. 阶段 3（推理）请求是软件一集一集**串行**放出的，同一时刻通常只有 1 个，这是正常的，也是故意的：下一集的请求里会带着上一集最后一段，让模型接着写站位。所以**不要抢先、不要乱序、不要把不同集同时分给不同的子智能体**；上一集没答完，下一集的请求根本还不存在。

### 判定完成之后：检查与重试

- **看 `batch.failed`**（`label` 是「第 N 集」或素材类型，`message` 是软件的原话）。
  把失败的集号重新发同一条命令（`episodes` 只填失败的），**每个阶段最多重试 2 轮**；还失败就停下汇报，附上软件的原话。
- 软件的常见失败原因和对策：
  - 「没有识别到分镜」「返回了 X 段，这一集的时长分割有 Y 段（多半是输出被截断）」→ 子智能体输出格式不对或没写完；重试时在子智能体提示词里加一句「必须完整输出全部 Y 段，宁可慢也不要截断」。
  - 「AI 未返回有效分集」→ 分集输出不是纯 JSON 数组；重试。
  - 「这一集还没有时长分割」→ 回到阶段 2 补这一集。
  - 「这一集的各段还没有命名」「还没有命名（场景 / 角色 / 道具）」→ 回到阶段 2.5 发 `name` 补这几集。
  - 命名请求被软件拒绝：「没有识别到分段」「AI 写了 X 段的名字，这一集有 Y 段」→ 子智能体没按「第N段 + 四行头行（+ 可选的【阶段】行）」逐段输出；重试时在提示词里加一句「必须逐段输出，共 Y 段，不能少、不能合并」。
  - 提取被拒绝「还没有推理分镜」→ 回到阶段 3 补这几集。
- **分割阶段的特别检查**：阶段 2 结束后看 `xipi status`——出现「⚠ 分割后没有时间标记的集」，说明这些集的分割没写时间标号（`--- 00:00 - 00:30` 写在段末，或 `=== [00:00-00:30] ===` 写在段首，两种软件都认），后面推理分镜一定失败：把这些集重新 `split`（重试额度另算）。
- **提取阶段的特别检查**：`created == 0`（没建出任何卡）软件不算失败，但几乎肯定是子智能体没按「这个人是：…」格式输出，要当失败重试 1 次再汇报。注意也可能是分镜头行里本来就没有这一类名字（比如没有道具）——软件这时不发请求，也就没有请求可答。
- **提取阶段的名字**：每张卡的名字必须就是请求里名单上的名字（不加「第N集的」、不加阶段；每块单独一行「起始集：N」，名单里写了「阶段：X」的再单独一行「阶段：X」，这两行软件读走、不进出图提示词）。名字被改了，匹配素材就挂不上图；软件会在右上角的结果里提醒，但提醒不进 `status.json`，所以子智能体要自己守住。
- **抽查**（便宜的）：阶段 2 结束后随机挑 1 集，让一个子智能体读 `user.txt` 和结果对比，看台词有没有被改动或丢失；发现问题就汇报，不要自己动手改。

### 取消

用户说停：发 `stop`。请求文件被软件删掉 = 这一步取消了；还在干活的子智能体回答前会发现并丢弃（`xipi answer` 会提示 CANCELLED），不用你处理。

## 子智能体任务模板（逐字使用，只替换 `<ID>`、`<XIPI路径>` 和 `<收件目录>`）

```
你是「嬉皮小剧场」的文字处理子智能体：软件把一个文字请求交给你，你就是原来的那个文字模型 API。

1. 运行：python3 <XIPI路径>/xipi.py --dir <收件目录> unpack <ID>（<收件目录> 是主智能体告诉你的那个，下面每条 xipi 命令也都带上它）
   - 如果输出里有「收件目录不对」：不是取消！什么都不要写，直接结束并回复「wrong-dir <ID>」，让主智能体处理。
   - 如果输出里有 CANCELLED：这一步已被取消，什么都不要写，直接结束并回复「cancelled <ID>」。
   - 否则它会打印一个工作目录，里面有：
       system.txt  必须完整遵守的工作要求（含输出格式）
       user.txt    要处理的输入
       meta.json   这是哪一步 / 哪个项目 / 哪一集；若 images 里有图片路径，用读图工具看那些图
2. 把 system.txt 当作完整的工作要求，对 user.txt 做处理，直接产出结果。**必须由你自己读、自己写，不许写脚本去生成，也不许参考别的项目或文件。**
   - 输出必须严格符合 system.txt 规定的格式；软件会按格式解析，格式不对整步重做。
   - 只输出结果正文：不要寒暄、不要解释、不要复述规则、不要外包代码块围栏（除非 system.txt 明确要求）。
   - 剧本里的台词、人名、场景名一律原样保留，不改写、不润色、不省略，除非 system.txt 明确要求。
   - 长输出要完整写完，不要截断、不要用「……」「以下省略」代替内容。
3. 把结果正文原样写进工作目录里的 answer.txt（用文件写入工具，不要手工拼 JSON）。
   写之前先对照 system.txt 自检一遍格式、段数、标记。
4. 运行：python3 <XIPI路径>/xipi.py --dir <收件目录> answer <ID>
   - 提示 CANCELLED：请求已被取消，丢弃即可。提示「收件目录不对」：不是取消，回复「wrong-dir <ID>」。
5. 实在做不了（输入明显不完整、要求互相矛盾）：运行 python3 <XIPI路径>/xipi.py --dir <收件目录> fail <ID> "具体原因"，不要硬编。

6. 如果 meta.json 里的 kind 是「推理分镜」：
   - 一集所有的段必须在**同一个回答里一次写完**，段与段之间站位连贯——前一段结尾时各角色的位置、朝向、手持道具，就是后一段【角色初始站位与朝向】的起点。不要把每段当成独立的小任务，不要每段都重新安排一套站位。
   - 如果 user.txt 开头有「【上一集最后一段…】」和「【承接说明】」：本集第一段若与它是同一场景，【角色初始站位与朝向】要从那一段结束时的状态接着写；不是同一场景就忽略它。那一段只用来承接，不要照抄，也不要重新输出。
   - **时间标记怎么读（最常见的误读，别踩）**：标号有两种写法，**以 user.txt 开头的「【时间标号说明】」为准**（里面写了本集一共几段、标号写在哪）：
     ① `--- 00:00 - 00:30` 写在**它上面那一段的末尾**，是那一段的时间标号，**不是下一段的标题**。所以最后一个标记后面没有内容是正常的，不是空段；开头第一段也不是「没标时间」——**这两点都不算输入不完整，不要因此 fail**；
     ② `=== [00:00-00:30] ===` 写在**它下面那一段的开头**，是这一段的标题，标号下面的内容属于这一段，不是上一段的结尾。标号行本身不是内容，不要写进分镜；第一个标号之前没有内容是正常的。
     两种写法都是「标号个数 = 段数」。
   - **同一场景连续多段，也必须每个 30 秒段单独一块**，不得把相邻的几段并成一块，也不得少写台词（并段、漏台词都会被软件的段数核对拦下，整集重来）。
   - 块数必须恰好等于这一集的时间标记个数，写完逐段数一遍：数以 `[场景][角色][道具]` 开头的行，要等于标记个数。

6.5 如果 meta.json 里的 kind 是「分段命名」：
   - 只做一件事：给 user.txt 的【本集分段】里的每一段写四行名字（有人在回忆 / 闪回里时再加一行【阶段】：周承山=四十岁，名字本身仍写基础名）；**不改写剧情、不复述台词**，输出里只有「第N段」和这几行。
   - 【项目里前面各集已经用过的名字】里已有的对象，名字**一字不差地沿用**；【本集原文】只用来判断年龄阶段、时间跳跃和地点。
   - 写完数一遍：「第N段」的个数必须等于【本集分段】的段数。

7. 如果 meta.json 里的 kind 是「提取角色」「提取场景」「提取道具」：
   - user.txt 开头有一份**名单**（名称已经定好，来自分镜头行）：**只为名单里的名字写，名字一字不改，不要新增、不要合并、不要漏掉**；名称不加「第N集的」、不加阶段词；每块按 system.txt 单独写一行「起始集：N」，名单里写了「阶段：X」的再单独写一行「阶段：X」。
   - 角色、道具的描述去名单后面的【原文】里找；场景的描述去【各场景用到它的分镜】里找（只写空间、陈设、固定设施、光线，不写人物、动作、台词、运镜）。
   - 名单里标「已有」的：本次里没有变化的不要重复输出，明确写了变化才输出新的一条。
   - 名单里写了「阶段：X」的不用写「参考」行（软件自己拿主时间线那张当参考图）。只有名单里的旧名字把阶段写进了名字（如「周承山十岁时期」），才在它那一块里单独写一行「参考：周承山」（写名单里或已有的那个基础名字）。
```

## 各类请求的输出要求（软件会校验，不合格 = 失败重来）

具体格式以请求里的 `system.txt` 为准（用户可能在软件设置里改过提示词）；下面列的是软件**一定会检查**的点
（软件只查格式，不查内容有没有丢——内容不丢、不改，是子智能体自己的责任）：

- **剧本分集**：纯 JSON 数组 `[{"title":"第 1 集","text":"本集全部正文"}, …]`，不要代码块围栏；每集 `text` 不能为空。各集正文连起来必须覆盖整部剧本，一字不丢（软件不查，抽查时要看）。
- **时长分割**：输出整集分割后的文字（场景行、△画面、台词；每段带一个时间标记，按分割提示词里写的格式——`--- 00:00 - 00:30` 写在段末，或 `=== [00:00-00:30] ===` 写在段首；每段还可以有 `【本段在场】：…` 一行，写本段画面里在场的人）。软件原样保存，`推理分镜` 靠这些时间标记数段数。
  **段末写法下，最后一个时间标记之后不要再有任何文字**（不要「结束」「完」「待续」之类；段首写法下，最后一段的结尾也别加）。软件只对「结束 / 完 / END」这类收尾词网开一面，别的文字会被当成多出来的一段，推理分镜时报「返回了 X 段，这一集的时长分割有 Y 段」。
- **分段命名**：`user.txt` 里有【项目里前面各集已经用过的名字】、【本集原文】和【本集分段】（按「第N段」编号）。输出**逐段**写：先一行「第N段」，下面四行 `【场景】：…` `【角色】：…` `【道具】：…` `【本段在场】：…`（这一段有人在回忆 / 闪回里时，在【角色】下面加一行 `【阶段】：周承山=四十岁`，没有就不写这一行），段与段之间空一行；**段数必须恰好等于【本集分段】里的段数，段号从 1 连续到最后**，少了 / 多了 / 段号乱了整集失败，什么都不写入。**名字必须沿用「前面各集已经用过的名字」里的写法，一字不差**；新对象才起新名字；同一角色在回忆 / 时间跳跃里的年龄阶段，名字仍写基础名，阶段写进【阶段】行（「周承山=四十岁」），**不要写成「周承山四十岁时期」**。不要输出名字以外的任何话。
- **提取角色 / 场景 / 道具**：按 `system.txt` 的块格式（「这个人是：…」「这个场景叫：…」「这个物品名称叫：…」）一块一个；软件按这些开头把输出切成卡片，没有这些开头就是 0 张卡。
  `user.txt` 开头是「【要提取的角色——名称已经定好，来自分镜头行…】」和一份**名单**：**只为名单里的名字写，名字一字不改，不要新增、不要合并、不要漏掉**（名称不加「第N集的」、不加阶段；每块单独写一行「起始集：N」，名单里写了「阶段：X」的再单独写一行「阶段：X」）。描述去哪找：角色、道具去名单后面的【原文】，场景去【各场景用到它的分镜】（场景只写空间、陈设、光线，不写人物和动作）。名单里标「已有」的，是前面各集已经提取过的（后面「前面各集已经提取过的…」列着）：本次里**没有变化的不要重复输出**，明确写了变化才输出新的一条。
  回答要一次写完：**输出被截断（写到一半停了）软件会当作失败**，写不完就如实说，别交半截。
- **推理分镜**：每个 30 秒段一块，**每块的第一行必须是 `[场景][角色][道具]` 三个方括号开头**（名字用这一段【场景】【角色】【道具】【本段在场】里写的，不改；只写基础名，这一段有【阶段】行时按那个阶段写外貌，不要把阶段写进名字，【阶段】行本身不抄进分镜）；块的数量必须**恰好等于**这一集时长分割里的段数（= 时间标记的个数，不管标号写在段末还是段首），少了 / 多了整集失败。少了多半是把同一场景相邻的几段并成了一块（也可能是被截断）；多了多半是把最后一个标记当成了一段。
- 看图请求（meta.json 里 `images` 非空）：先读图再回答。
